# Discussions dispatcher: offline implementation and cutover

Status: draft engineering source only. This change does not enable Discussions, create an App or script trigger, change repository variables, retrieve PSU menus, or dispatch a workflow. With `LIONLOG_DISPATCH_MODE` unset, the existing 05:17 New York cron path remains the default after merge. External mode requires `LIONLOG_DISPATCH_MODE=external` and a separate `LIONLOG_EXTERNAL_DISPATCH_ACTIVATION` gate. The existing source authorization, checkpoint, publication, coverage and manual gates still apply.

## Route and one-opportunity rule

The standalone `dispatcher/Code.gs` uses one five-minute Apps Script trigger, installed once through `installLionLogDispatcherTrigger()`. Every tick checks a local New York due gate beginning 05:17 and ending strictly before 12:15; the first eligible tick claims the day. Under a script lock it persists `lionlog-dispatch-claim:YYYY-MM-DD` in Script Properties **before** making any network request. The script mints a GitHub App installation token and makes one GraphQL `addDiscussionComment` POST with body `lionlog-dispatch.v1:YYYY-MM-DD` on one pinned Discussion. A lost response, exception or invalid readback leaves the date claimed. There is no automatic repost or recovery loop. The separate App needs only Discussions write and Metadata read on this repository. Keep its private key in restricted Script Properties. This App is distinct from the publication writer App and the monitor's read-only token.

The default-branch workflow has mutually exclusive modes. With the mode variable unset or any value other than `external`, only the legacy schedule job can publish and it checks out the approved production SHA. In external mode, schedule events skip publication and only `discussion_comment.created` can publish after its activation, exact receiver commit SHA, bot numeric **user ID**, Discussion node ID and existing gates are set. The external route checks out the exact receiver commit from `main` with Actions write, Contents read and Discussions read. The orchestrator verifies the webhook's repository, Discussion, comment, bot sender, body, timestamps, New York date, GraphQL comment readback, Actions receiver run ID/attempt/actor/path/SHA/title and complete paginated histories. A same-day cron-triggered run is harmless only when its authenticated run readback proves a terminal `skipped` conclusion on this exact audited receiver SHA; an old revision, active run or non-skipped conclusion blocks the external route. The receiver concurrency group serializes executions; multiple same-day receiver runs, reruns, missing history or conflicting producer/promotion history stop before retrieval. The existing authenticated checkpoint, public predecessor, production pin, request budget, complete coverage with zero invalid-name omissions, freshness, promotion and checkpoint gates remain in force. An admitted late first start uses recovery mode. A received event at or after 12:15 fails before any network read by the orchestrator.

The orchestrator sends downstream `workflow_dispatch` with `return_run_details=true`. A missing or ambiguous returned run ID ends unattended processing, and each returned ID is checked against the exact workflow, pinned production SHA, branch, first attempt and terminal success. Do not retry an uncertain request. The protected manual promotion and rollback paths are unchanged.

## Read-only monitor correlation

The receiver writes `discussion-binding.json` atomically after admission and after each dispatch or verified stage. Its always-run artifact is named `lionlog-discussion-binding-<receiver-run-id>-1`. The cumulative JSON contains version `lionlog.discussion-binding.v1`, stage, service date, exact comment ID/node ID, receiver run ID/SHA, then candidate, promotion and checkpoint run IDs as they become known. `complete` additionally contains the release ID. `scripts/discussion-binding.ts` validates the shape and stage-dependent fields against an independently read receiver run. The artifact's presence or an ID labeled `*-dispatched` alone does **not** prove downstream admission or success.

`monitor/DispatchAdapter.gs` is deployable source for the read-only hosted monitor. Add that file during cutover, pass the existing signed checkpoint/public proof (`completeEvidence`, admission state and exact candidate ID, public release/freshness/integrity fields) to `collectLionLogMonitorEvidence(now, publicationProof)`, and use `evaluateLionLogDispatchPoll` for the current incident state before the hosted send/deduplication step. The hosted runner must treat a collector exception as evidence unavailable while preserving prior open incidents. Set `LIONLOG_MONITOR_DISPATCH_MODE` to `schedule` (or leave it unset) until cutover; then set it to `external` with the audited receiver SHA, bot user ID and production SHA/branch. Reuse the existing token as `LIONLOG_MONITOR_GITHUB_TOKEN`; it needs only Actions read, Contents read and Metadata read. This source does not send mail or edit the hosted project in this PR.

The adapter uses GETs to enumerate complete receiver and downstream histories. While the receiver is running, it reports observed but **unbound** producer/promotion/writer stage hints and marks admission unknown. A binding artifact is expected only after the receiver job finishes; an absent artifact while it runs or during a ten-minute terminal upload lag is `binding-pending`, not proof of no dispatch. A definitive terminal failure still alerts immediately. After that lag, no artifact is `binding-missing` and raises evidence-unavailable; incomplete/conflicting reads also fail closed. For a present artifact it requires exact name, run/SHA, unexpired status, wrapper SHA-256, single expected JSON entry, stage fields and exact downstream run readback. It accepts admission proof only when the existing collector's candidate run ID equals the bound ID. The hosted monitor retains its independent checkpoint/public-release checks and existing MailApp/deduplication policy. No monitor write permission, dispatcher App key or PSU access is added.

## Staged cutover (owner operations after review)

1. Independently audit this PR and its exact head; merge only after CI. Confirm a source-authorized, known-good checkpoint and a reviewed production commit containing the supported downstream workflows. Set `LIONLOG_PRODUCTION_REF` and `LIONLOG_PRODUCTION_SHA` to that immutable production revision under the existing release procedure. Set `LIONLOG_DISPATCH_RECEIVER_SHA` to the audited default-branch merge commit. Changes to either revision require re-review and repinning.
2. Leave `LIONLOG_DISPATCH_MODE` unset and both external activation gates unset after merge. The legacy cron stays active under its existing refresh/source settings. Drain and inspect queued/running old schedule runs and complete schedule/producer/promotion history before switching modes on a clean service date, preferably before 05:17. Temporarily disable the existing refresh activation while draining old-revision queued runs; an old workflow revision does not know the new mode variable. The legacy schedule run `42696495026` arrived November 9 at 15:48 New York and was rejected by the 12:15 cutoff; its lateness shows why old refs/reruns must be considered. A historic run on another branch may still be manually dispatchable and must not be mistaken for this external route.
3. Enable repository Discussions and create one dedicated Discussion. Provision a separate GitHub App installed only on `CrunchyBrunch/lionlog` with Discussions write and Metadata read. Store its App ID, installation ID, private key and exact Discussion node ID in the standalone Apps Script properties. Install the five-minute trigger and verify its New York due gate. Keep the script activation unset. Deploy the read-only monitor adapter, test its collector/proof integration, and retain `schedule` monitor mode until the route switch.
4. For a harmless event test, set only `LIONLOG_DISPATCH_PROBE_ACTIVATION=ENABLE_LIONLOG_DISPATCH_PROBE`, create a test Discussion comment, and inspect the probe job and webhook/run readback. The probe has `permissions: {}` and no checkout or production dispatch. Confirm that the App bot's **numeric user ID** (not App ID or installation ID), comment IDs, Discussion node ID, actor and default-branch receiver SHA match. Clear the probe variable afterward. A probe run consumes that service date for the receiver's first-opportunity history gate; activate on a later clean date. The GitHub Discussions workflow event is public preview; validate its actual behavior before relying on it.
5. After the harmless event identity and readback are confirmed, choose a later clean service day and recheck no queued/running old-revision scheduler. Set the receiver's bot/Discussion variables, existing standing/source/production variables, and `LIONLOG_DISPATCH_MODE=external` before that day's 05:17 schedule. Set `LIONLOG_EXTERNAL_DISPATCH_ACTIVATION=ENABLE_LIONLOG_EXTERNAL_DISPATCH`, switch the monitor mode to `external`, restore existing refresh activation if it was temporarily disabled, and set the Apps Script `LIONLOG_DISPATCH_ACTIVATION` last under an owner-recorded activation. Check one ordinary run, exact run correlation, monitor readback and public checkpoint. If any readback is missing, stop and investigate; do not repost an already claimed date.

The prior native-cron activation guide in `docs/daily-publication-activation.md` remains applicable while mode is unset. Its schedule-specific route and activation ordering are superseded only after the owner completes the mode switch. Source permission, protected environments and checkpoint bootstrap remain independent prerequisites.
