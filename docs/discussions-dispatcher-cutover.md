# Discussions dispatcher: offline implementation and cutover

Status: draft engineering source only. This change does not enable Discussions, create an App or script trigger, change repository variables, retrieve PSU menus, or dispatch a workflow. With `LIONLOG_DISPATCH_MODE` unset, the existing 05:17 New York cron path remains the default after merge. External mode requires `LIONLOG_DISPATCH_MODE=external` and a separate `LIONLOG_EXTERNAL_DISPATCH_ACTIVATION` gate. The existing source authorization, checkpoint, publication, coverage and manual gates still apply.

## Route and one-opportunity rule

The standalone `dispatcher/Code.gs` uses one five-minute Apps Script trigger, installed once through `installLionLogDispatcherTrigger()`. Every tick checks a local New York due gate beginning 05:17 and ending strictly before 12:15; the first eligible tick claims the day. Under a script lock it persists `lionlog-dispatch-claim:YYYY-MM-DD` in Script Properties **before** making any network request. The script mints a GitHub App installation token and makes one GraphQL `addDiscussionComment` POST with body `lionlog-dispatch.v1:YYYY-MM-DD` on one pinned Discussion. A lost response, exception or invalid readback leaves the date claimed. There is no automatic repost or recovery loop. The separate App needs only Discussions write and Metadata read on this repository. Keep its private key in restricted Script Properties. This App is distinct from the publication writer App and the monitor's read-only token.

The default-branch workflow has mutually exclusive modes. With the mode variable unset or any value other than `external`, the legacy schedule remains active and ultimately checks out the approved production SHA. In external mode, schedule events skip publication and only a pinned bot's exact `discussion_comment.created` identity can enter the privileged publish job. The cheap job gate checks repository, sender, comment author, bot login, Discussion, unedited timestamp, prefix, receiver SHA and activation before job concurrency. The probe is outside that concurrency group; either probe flag or external activation prevents the other job from running, including when both flags are set. The runner repeats full event, New York date, GraphQL readback and Actions run checks before downstream dispatch.

The shared durable reservation is the first authenticated, non-skipped receiver **Actions run** plus its run-bound `lionlog-day-reservation-YYYY-MM-DD` artifact. The default-branch `scripts/shared-opportunity.ts` checks the run history before the production checkout. The serialized job uploads the reservation artifact before any producer request. Immediately before the orchestrator, it checks both the history and the exact artifact name, digest, run ID, repository ID and SHA again; the external orchestrator repeats those checks before its candidate POST. It enumerates complete schedule history and bot-actor-filtered Discussion history, reads back candidate comments by exact node ID, and ignores unrelated human comments and unrelated bot Discussions/body. A same-day cron run is harmless only when readback proves a terminal `skipped` conclusion on the audited receiver SHA. A first eligible run and uploaded reservation remain in GitHub after runner loss or an ambiguous downstream response, so a later receiver cannot dispatch again. Job-level concurrency serializes eligible work; simultaneous visible opportunities fail closed. Keep the bot login, numeric ID and Discussion pin through the entire service day after external activation. Old workflow revisions must be drained before cutover because they cannot perform this new shared check. The existing authenticated checkpoint, public predecessor, production pin, request budget, complete coverage with zero invalid-name omissions, freshness, promotion and checkpoint gates remain in force. An admitted late first start uses recovery mode. A received event at or after 12:15 fails before any network read by the shared checker.

The orchestrator sends downstream `workflow_dispatch` with `return_run_details=true`. A missing or ambiguous returned run ID ends unattended processing, and each returned ID is checked against the exact workflow, pinned production SHA, branch, first attempt and terminal success. Do not retry an uncertain request. The protected manual promotion and rollback paths are unchanged.

## Read-only monitor correlation

The receiver writes `discussion-binding.json` atomically after admission and after each dispatch or verified stage. Its always-run artifact is named `lionlog-discussion-binding-<receiver-run-id>-1`. The cumulative JSON contains version `lionlog.discussion-binding.v1`, stage, service date, exact comment ID/node ID, receiver run ID/SHA, then candidate, promotion and checkpoint run IDs as they become known. `complete` additionally contains the release ID. `scripts/discussion-binding.ts` validates the shape and stage-dependent fields against an independently read receiver run. The artifact's presence or an ID labeled `*-dispatched` alone does **not** prove downstream admission or success.

`monitor/DispatchAdapter.gs` is deployable source for the read-only hosted monitor. Add that file during cutover, pass the existing signed checkpoint/public proof (`completeEvidence`, admission state and positive exact candidate ID, release ID, public release/freshness/integrity fields) to `collectLionLogMonitorEvidence(now, publicationProof)`, and use `evaluateLionLogDispatchPoll` for the current incident state before the hosted send/deduplication step. The hosted runner must treat a collector exception as evidence unavailable while preserving prior open incidents. Set `LIONLOG_MONITOR_DISPATCH_MODE` to `schedule` (or leave it unset) until cutover; then set it to `external` with the audited receiver SHA, bot numeric ID/login, Discussion node ID and production SHA/branch. Reuse the existing token as `LIONLOG_MONITOR_GITHUB_TOKEN`; it needs only Actions read, Contents read and Metadata read. This source does not send mail or edit the hosted project in this PR.

The adapter uses bot-actor-filtered GETs and the GitHub-generated run title to ignore unrelated Discussions without a Discussions-read grant. While the receiver is running, it reports observed but **unbound** producer/promotion/writer stage hints and marks admission unknown. A binding artifact is expected only after the receiver job finishes; an absent artifact while it runs or during a ten-minute terminal upload lag is `binding-pending`, not proof of no dispatch. A definitive terminal failure, three-hour deadline and independently confirmed public-integrity mismatch remain actionable during that wait, including a running receiver aged 342 minutes. Unknown evidence preserves open incidents until affirmative resolution. After the terminal lag, no artifact is `binding-missing` and raises evidence-unavailable. A present artifact requires exact name, run/SHA, unexpired status, wrapper SHA-256, one JSON entry, stage fields, downstream attempt/conclusion and release-ID agreement with independent proof. Admission attaches only when both candidate IDs are positive and identical. The hosted monitor retains independent checkpoint/public-release checks and MailApp/deduplication policy. No monitor write permission, dispatcher App key or PSU access is added.

## Staged cutover (owner operations after review)

1. Independently audit this PR and its exact head; merge only after CI. Confirm a source-authorized, known-good checkpoint and a reviewed production commit containing the supported downstream workflows. Set `LIONLOG_PRODUCTION_REF` and `LIONLOG_PRODUCTION_SHA` to that immutable production revision under the existing release procedure. Set `LIONLOG_DISPATCH_RECEIVER_SHA` to the audited default-branch merge commit. Changes to either revision require re-review and repinning.
2. Leave `LIONLOG_DISPATCH_MODE` unset and both external activation gates unset after merge. The legacy cron stays active under its existing refresh/source settings. Drain and inspect queued/running old schedule runs and complete schedule/producer/promotion history before switching modes on a clean service date, preferably before 05:17. Temporarily disable the existing refresh activation while draining old-revision queued runs; an old workflow revision does not know the new mode variable. The legacy schedule run `42696495026` arrived November 9 at 15:48 New York and was rejected by the 12:15 cutoff; its lateness shows why old refs/reruns must be considered. A historic run on another branch may still be manually dispatchable and must not be mistaken for this external route.
3. Enable repository Discussions and create one dedicated Discussion. Provision a separate GitHub App installed only on `CrunchyBrunch/lionlog` with Discussions write and Metadata read. Store its App ID, installation ID, private key and exact Discussion node ID in the standalone Apps Script properties. Install the five-minute trigger and verify its New York due gate. Keep the script activation unset. Deploy the read-only monitor adapter, test its collector/proof integration, and retain `schedule` monitor mode until the route switch.
4. For a harmless event test, set only `LIONLOG_DISPATCH_PROBE_ACTIVATION=ENABLE_LIONLOG_DISPATCH_PROBE`, create a test Discussion comment, and inspect the probe job and webhook/run readback. The probe has `permissions: {}` and no checkout or production dispatch. It is mutually exclusive with privileged publication even if both flags are accidentally set. Confirm the App bot's **numeric user ID and login** (not App ID or installation ID), comment IDs, Discussion node ID, actor and default-branch receiver SHA. Clear the probe variable afterward. Use a later clean service date for activation. The GitHub Discussions workflow event is public preview; validate its actual behavior before relying on it.
5. After harmless event identity and readback are confirmed, choose a later clean service day and recheck no queued/running old-revision scheduler. Set the receiver's bot ID, bot login and Discussion node ID; keep them pinned through the service day, including any mode rollback. Set existing standing/source/production variables and `LIONLOG_DISPATCH_MODE=external` before that day's 05:17 schedule. Set `LIONLOG_EXTERNAL_DISPATCH_ACTIVATION=ENABLE_LIONLOG_EXTERNAL_DISPATCH`, switch the monitor mode to `external`, restore existing refresh activation if it was temporarily disabled, and set the Apps Script `LIONLOG_DISPATCH_ACTIVATION` last under an owner-recorded activation. Check one ordinary run, exact run correlation, monitor readback and public checkpoint. If any readback is missing, stop and investigate; do not repost an already claimed date.

The prior native-cron activation guide in `docs/daily-publication-activation.md` remains applicable while mode is unset. Its schedule-specific route and activation ordering are superseded only after the owner completes the mode switch. Source permission, protected environments and checkpoint bootstrap remain independent prerequisites.
