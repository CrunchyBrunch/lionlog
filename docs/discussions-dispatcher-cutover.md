# Discussions dispatcher: offline implementation and cutover

Status: draft engineering source only. This change does not enable Discussions, create an App or script trigger, change repository variables, retrieve PSU menus, or dispatch a workflow. `LIONLOG_EXTERNAL_DISPATCH_ACTIVATION` is a new separate receiver gate and must remain unset until the full cutover. The existing source authorization, checkpoint, publication, coverage and manual gates still apply.

## Route and one-opportunity rule

The standalone `dispatcher/Code.gs` time trigger wakes at 05:17 America/New_York, with a bounded late window ending strictly before 12:15. Under a script lock it persists `lionlog-dispatch-claim:YYYY-MM-DD` in Script Properties **before** making any network request. The script mints a GitHub App installation token and makes one GraphQL `addDiscussionComment` POST with body `lionlog-dispatch.v1:YYYY-MM-DD` on one pinned Discussion. A lost response, exception or invalid readback leaves the date claimed. There is no automatic repost, recovery loop, or second route to Actions. The separate App needs only Discussions write and Metadata read on this repository. Keep its private key in restricted Script Properties. This App is distinct from the publication writer App and the monitor's read-only token.

GitHub's default-branch `discussion_comment.created` workflow receives the event. Its publish job is inert unless the external activation variable, exact receiver commit SHA, bot numeric **user ID**, Discussion node ID, existing refresh/source/standing-policy variables, production pin and writer ID are set. It checks out the exact receiver commit from `main` with Actions write, Contents read and Discussions read. The orchestrator verifies the webhook's repository, Discussion, comment, bot sender, body, timestamps, New York date, GraphQL comment readback, Actions receiver run ID/attempt/actor/path/SHA/title, complete paginated receiver history and absence of same-day legacy schedule history. The receiver concurrency group serializes executions; multiple same-day receiver runs, reruns, missing history or conflicting producer/promotion history stop before retrieval. The existing authenticated checkpoint, public predecessor, production pin, request budget, complete coverage with zero invalid-name omissions, freshness, promotion and checkpoint gates remain in force. An admitted late first start uses recovery mode. A received event at or after 12:15 fails before any network read by the orchestrator.

The orchestrator sends downstream `workflow_dispatch` with `return_run_details=true`. A missing or ambiguous returned run ID ends unattended processing, and each returned ID is checked against the exact workflow, pinned production SHA, branch, first attempt and terminal success. Do not retry an uncertain request. The protected manual promotion and rollback paths are unchanged.

## Read-only monitor correlation

The receiver writes `discussion-binding.json` atomically after admission and after each dispatch or verified stage. Its always-run artifact is named `lionlog-discussion-binding-<receiver-run-id>-1`. The cumulative JSON contains version `lionlog.discussion-binding.v1`, stage, service date, exact comment ID/node ID, receiver run ID/SHA, then candidate, promotion and checkpoint run IDs as they become known. `complete` additionally contains the release ID. `scripts/discussion-binding.ts` validates the shape and stage-dependent fields against an independently read receiver run. The artifact's presence or an ID labeled `*-dispatched` alone does **not** prove downstream admission or success.

The existing monitor can use its Actions read and Contents read token: GET the receiver run, GET that run's artifact list, require one unexpired exact-name artifact bound to its run ID/SHA and digest, GET and verify its ZIP wrapper, parse its single JSON entry, then GET each named downstream run and retain its current independent checkpoint/public-release checks. Treat a missing, incomplete or conflicting artifact as an observation failure, not as proof of no dispatch. The four alert categories and send/deduplication policy remain the monitor's; this correlation adds no monitor write permission, App key or PSU access.

## Staged cutover (owner operations after review)

1. Independently audit this PR and its exact head; merge only after CI. Confirm a source-authorized, known-good checkpoint and a reviewed production commit containing the supported downstream workflows. Set `LIONLOG_PRODUCTION_REF` and `LIONLOG_PRODUCTION_SHA` to that immutable production revision under the existing release procedure. Set `LIONLOG_DISPATCH_RECEIVER_SHA` to the audited default-branch merge commit. Changes to either revision require re-review and repinning.
2. Leave `LIONLOG_EXTERNAL_DISPATCH_ACTIVATION` and the Apps Script activation unset. Drain and inspect old queued/running schedule runs and complete same-day schedule/producer/promotion history. The legacy schedule run `42696495026` arrived November 9 at 15:48 New York and was rejected by the 12:15 cutoff; its lateness shows why old queued runs must be considered, including old refs/reruns. Remove/disable every old schedule source before new activation. A historic run on another branch may still be manually dispatchable and must not be mistaken for this external route.
3. Enable repository Discussions and create one dedicated Discussion. Provision a separate GitHub App installed only on `CrunchyBrunch/lionlog` with Discussions write and Metadata read. Store its App ID, installation ID, private key and exact Discussion node ID in the standalone Apps Script properties. Provision a daily time trigger and verify its New York execution timing. No trigger should be active while the script gate is unset.
4. For a harmless event test, set only `LIONLOG_DISPATCH_PROBE_ACTIVATION=ENABLE_LIONLOG_DISPATCH_PROBE`, create a test Discussion comment, and inspect the probe job and webhook/run readback. The probe has `permissions: {}` and no checkout or production dispatch. Confirm that the App bot's **numeric user ID** (not App ID or installation ID), comment IDs, Discussion node ID, actor and default-branch receiver SHA match. Clear the probe variable afterward. A probe run consumes that service date for the receiver's first-opportunity history gate; activate on a later clean date. The GitHub Discussions workflow event is public preview; validate its actual behavior before relying on it.
5. After the harmless event identity and readback are confirmed, set the receiver's bot/Discussion variables, existing standing/source/production variables and `LIONLOG_EXTERNAL_DISPATCH_ACTIVATION=ENABLE_LIONLOG_EXTERNAL_DISPATCH`. Set the Apps Script `LIONLOG_DISPATCH_ACTIVATION` last, under an owner-recorded activation. Check one ordinary run, exact run correlation, monitor readback and public checkpoint. If any readback is missing, stop and investigate; do not repost an already claimed date.

The prior native-cron activation guide in `docs/daily-publication-activation.md` records the existing publication authority and safety gates. Its schedule-specific route and activation ordering are superseded by this staged cutover once the old schedule is drained. Source permission, protected environments and the checkpoint bootstrap remain independent prerequisites.
