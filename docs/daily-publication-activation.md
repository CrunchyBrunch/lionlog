## Monitoring and recovery

Configure GitHub Actions failure notifications for the owner and watch the `Daily verified LionLog publication` run, its exact three downstream run links in the step summary, public release marker, and checkpoint branch. A failure before Pages submission leaves the previous public bytes in place. A failure after submission can leave new public bytes with an old checkpoint; investigate and reconcile that state before the next day. The app's existing freshness and retention labels apply. A candidate or promotion failure does not trigger another scheduled full scrape. A failed public verification cannot advance the checkpoint.

If the elapsed window expires after a dispatch request has begun, GitHub may still accept that request or complete its workflow after the scheduler stops. A missing or late dispatch response does not prove no run started. Do not retry automatically; inspect authenticated run history, the public release marker, and the checkpoint before any owner-authorized recovery.

GitHub documents that schedule events can be delayed or dropped and can be disabled after 60 days of inactivity in public repositories. Checkpoint commits on a non-default state branch are **not** established here as satisfying GitHub's activity criterion. Native Actions failure notifications report a run that starts and fails; they cannot detect an event that never starts. The owner needs an independent heartbeat check if absence detection is required for indefinite daily operation. This PR does not set up an external scheduler or monitor.
